## BE-11 · Midtrans Notification URL (manual)

**Prasyarat sudah terpenuhi** (BE-05, BE-10): `POST https://be.aina.ai.id/v1/billing/midtrans` sampai ke
Worker tanpa challenge, dan ditolak `403 Forbidden` oleh pengecekan `signature_key` kalau signature-nya
palsu.

Langkah:
1. Dashboard Midtrans (**Production**) → Settings → Configuration → **Payment Notification URL** →
   `https://be.aina.ai.id/v1/billing/midtrans` → Save.
2. Kalau Recurring/Pay Account Notification URL juga terisi workers.dev, ganti ke URL yang sama.
3. (Opsional) Ulangi di environment Sandbox.
4. Verifikasi: transaksi kecil → order `paid` → di Workers Logs ada `POST /v1/billing/midtrans` dengan host
   `be.aina.ai.id` dan status 200. Logs disampling 10%, jadi bukti utamanya status order di akun.

Rollback: kembalikan URL ke `https://badi-cloud.faisalmashuri16.workers.dev/v1/billing/midtrans`. Order yang
notifikasinya hilang tetap diselesaikan oleh cron harian dan saat app membaca akun (cek `/v2/{order}/status`).

### Catatan: tombol "Test notification URL" di dashboard gagal (2026-11-09)
- `https://be.aina.ai.id/v1/billing/midtrans` → *"Test failed. An internal error has occurred."*
- `https://badi-cloud.faisalmashuri16.workers.dev/v1/billing/midtrans` (URL lama yang selama ini dipakai
  di production) → **gagal juga, dengan pesan yang sama**.

Kesimpulan: kegagalan ini **tidak terkait domain baru** dan tidak menunjukkan pemblokiran Cloudflare,
karena workers.dev tidak melewati zone `aina.ai.id`. Penyebab paling mungkin: payload tes Midtrans
memakai data contoh yang `signature_key`-nya tidak cocok dengan server key, sehingga handler kita
(`midtrans()`, `cloud/src/lib.rs`) menjawab 403. Ini sesuai panduan Midtrans: notifikasi dengan signature
yang tidak cocok diabaikan. Ini inferensi; dokumentasi Midtrans tidak menjelaskan isi payload tombol tes.

**Bukti yang menentukan adalah transaksi nyata** (langkah 4), bukan tombol tes.

### Transaksi asli (2026-11-09)
- `MIDTRANS_SERVER_KEY` ternyata masih key sandbox, padahal `MIDTRANS_PRODUCTION = "1"`. Faisal sudah
  menggantinya dengan key production (Worker version `f6800c00-45d5-4f30-850c-9dd98c1389e8`, sumber
  "Secret Change", 08:56Z).
- Checkout `badi-6-1794214934520-984227` (Rp49.000) membuka Snap production, dan dibayar dengan QRIS.
- `wrangler tail --format json --method POST` saat tes dan bayar:
  - tombol "Test notification URL" → `POST /v1/billing/midtrans` **403** (signature payload tes tidak cocok,
    jadi ditolak sesuai desain)
  - POST **200**: awalnya dikira notifikasi asli. **Koreksi:** filter tail hanya `--method POST`, dan detail
    order di dashboard (lihat di bawah) menunjukkan notification log **kosong**. Jadi 200 itu hampir pasti
    `POST /v1/checkout` saat order dibuat.
- Order sebenarnya: `badi-6-1794215337541-afc51d`, QRIS (Bank Jago via GoPay), Settlement 16:09,
  item `topup_small`. **Notification log: kosong.** Midtrans tidak mengirim notifikasi untuk order ini.
- Redirect ke `aina.ai.id/terima-kasih`, dan order selesai lewat **jalur cadangan**: `GET /v1/orders/{id}`
  → `reconcile()` → `/v2/{order}/status`.
- Payload tombol tes (IP 149.129.238.95, `okhttp/4.12.0`) sampai ke Worker `f6800c00`, lalu 403 di cek
  signature, tanpa exception.
- Di halaman QRIS Snap perlu klik "Cek status" sebelum redirect. Ini perilaku standar Snap untuk
  pembayaran QRIS, bukan dari backend.
- Tindak lanjut: di dashboard Midtrans → Transactions → order di atas → riwayat notifikasi, harus tercatat
  HTTP 200 ke `be.aina.ai.id`. Ini memastikan baris 200 di tail memang notifikasi Midtrans, karena filter
  tail hanya `--method POST`.
- Dampak kunci sandbox sebelumnya: selama key sandbox terpasang, checkout production tidak bisa dibuat.
  Cek apakah ada keluhan atau order gagal di periode itu.

### Akar masalah & perbaikan (2026-11-09, ±17:00 WIB)
- Setelah key diganti, notifikasi asli (UA `Veritrans`) **juga** dijawab 403. Pembayaran sukses hanya
  lewat jalur cadangan.
- Log diagnostik ditambahkan di `midtrans()`: order, status_code, gross_amount, awalan signature, dan
  sidik jari key (12 hex SHA-256 + panjang, tanpa key-nya). Hasil log: `key_sha256=7117f0da6548… key_len=35`.
- Faisal memberikan **Signature Secret Key** dari dashboard. Dicek secara lokal:
  - sidik jari `6381e9b384fd…`, **berbeda** dari key di Worker
  - `SHA512(order_id+status_code+gross_amount+key)` **cocok persis** untuk payload tes `a24f72c0` dan
    `fbde36e3`
- **Akar masalah:** akun Midtrans ini menandatangani notifikasi dengan **Signature Secret Key** yang
  terpisah dari **Server Key** (yang dipakai untuk API). Kode lama memverifikasi notifikasi dengan Server
  Key.
- **Perbaikan:** secret baru `MIDTRANS_SIGNATURE_KEY` dipakai untuk verifikasi notifikasi (fallback ke
  `MIDTRANS_SERVER_KEY` kalau kosong). `MIDTRANS_SERVER_KEY` tetap dipakai untuk API. Didokumentasikan
  di `wrangler.toml` dan `README.md`.
- **Hasil:** setelah deploy dan `wrangler secret put MIDTRANS_SIGNATURE_KEY`, dashboard Midtrans menampilkan
  **"Tested ✓"** untuk `https://be.aina.ai.id/v1/billing/midtrans`. **BE-11 selesai.**
- Tindak lanjut: regenerate Signature Secret Key (sempat tertulis di chat), lalu `secret put` ulang.
  Pantau notifikasi asli berikutnya di "View notification history" (harus sukses).

### Yang ikut pindah di app baru
`base()` dipakai untuk semua panggilan API dan **login** (commit `87f311e` "Keep signing in on the Worker's
address for now"). Di app baru, browser login membuka `https://be.aina.ai.id/login?app_state=…`. Ini sudah
diverifikasi di BE-10: host ini mengembalikan 302 ke Google dengan callback `aina.ai.id`. Halaman
Ketentuan dan Privasi tetap lewat `BADI_WEB_URL` (`aina.ai.id/api`).

User yang mengisi `cloudUrl` sendiri di config tidak terpengaruh.
